# 二、学生对课题的综合理解

## （一）课题目的及意义

小说持续创作不仅涉及当前段落的表达，还需要维护人物经历与关系、世界观规则、大纲和前文章节。随着内容积累，作者需要反复查阅资料、调整情节，并判断新内容是否符合已有设定。大语言模型在语言理解与生成方面的发展，为构思、续写和修改提供了技术条件[1-2]。本课题关注如何把这些能力放入作者日常使用的创作系统，使资料管理、正文编辑和智能辅助相互衔接。

国内相关研究已涉及生成控制、叙事生成和长文本处理。提示学习与受控文本生成综述分别从任务表达、生成条件等方面整理方法，为组织作者要求提供参考[5-6]。中文故事结尾生成研究采用双向对比训练，并结合自动指标和人工评价考察结果，其实验对象是结尾句，不能直接推广到长篇章节续写[7]。长文本推断综述讨论计算、存储与时延问题；幻觉及安全隐私综述则说明生成可靠性和数据保护需要单独考虑[3-4,8]。这些研究支持问题识别，不直接证明本系统的上下文方案有效。

创作者使用AI的方式也是相关研究的重要内容。对18名签约网络文学作者的访谈显示，部分受访者会限制AI用途，并保留自身构思和选择；该样本不能代表全部网络文学作者[9]。理论与案例研究也讨论作者主体性和数据依赖，强调作者对工具反馈的判断[10]。另外，两篇Web系统案例展示了角色、模块、数据库和服务实现的组织方式，可供本课题工程设计参考，但不构成框架性能或安全优势的证明[11-12]。

国外研究从协同操作、长故事生成及一致性评价等方面展开。Wordcraft在故事编辑器中提供预设和自定义生成、修改操作，研究作者如何使用模型建议，其短故事实验不能代表长期小说创作效果[13]。Re³以规划、起草、重写和编辑组织长故事生成，在生成过程中更新计划与前文信息[14]。Lost in Stories研究人物、时间和世界规则等一致性错误，并通过基准与检查方法进行专门评价[15]。这些工作为作者控制、上下文选取和冲突提示提供了参考；本项目的Writing Skill、Context Management及具体调用流程仍需自行设计与验证。

本课题拟设计并实现基于Spring Boot、Vue与大语言模型的Web小说智能辅助创作系统，将作品、卷章节、创作资料、正文编辑和过程管理与智能辅助结合。AI生成内容作为候选，由作者决定采用、修改、重新生成或放弃，未经确认不覆盖正式稿件。其实际应用意义是为持续小说创作提供统一的资料与写作环境；软件工程实践意义则是综合运用需求分析、架构与数据库设计、前后端开发、认证、AI接入和测试方法，考察模型能力如何与真实业务流程结合，不预先承诺创作质量或效率提升。

## （二）课题研究的主要内容

课题拟围绕创作者和轻量管理员分析需求，设计前后端分离架构及业务数据关系。常规创作部分以邮箱认证、作品与卷章节管理、富文本正文编辑为基础，组织人物及关系、世界观、大纲、素材和灵感资料，并安排写作计划、创作统计、搜索、行业创作趋势、稿件导入导出和版本历史等功能。签到、灵石激励与兑换、拼字房间、禅模式和音乐归入创作激励与沉浸体验，作为辅助业务统一设计。TXT导入拟支持整本单章节与规则分章，经过解析预览和作者确认后进入统一数据模型。

智能创作部分拟通过Writing Skill组织大纲规划、人物塑造、情节构思、上下文续写、文本润色和一致性检查六类任务，明确输入、资料需求、提示词与输出处理。Context Management将按任务组织上下文；MCP Resource和Tool负责访问已保存资料及必要查询能力；外部LLM生成候选或检查结果。设计将重点说明这些部分如何与正文编辑及作者确认衔接。

系统完成后拟开展功能、性能、安全性和可靠性测试，针对续写、一致性检查及作者确认设置专项验证，并单独检查真实MCP调用链路。实现说明、数据库文档、测试记录及部署演示材料将与论文保持对应。

## （三）拟解决的主要问题和最终目标

**A. 拟解决的主要问题**

一是持续积累的作品设定、人物、大纲与章节需要统一组织，避免创作取材与正文脱节；二是不同智能任务所需信息不同，续写需要结合前文和设定，不能把全部资料无差别提交模型；三是人物、时间、情节和世界规则可能发生冲突，需要给出可复核的依据，而非将所有变化判为错误；四是候选与正式稿件需要明确分离，使作者掌握保存决定权；五是智能任务访问资料需要统一协议入口，同时保持作品归属和访问权限。课题拟处理上述软件应用问题，不以彻底消除长篇一致性错误为目标。

**B. 最终目标**

完成可运行的Web小说智能辅助创作系统，覆盖已确认的认证、创作业务和轻量管理员功能，落实六类Writing Skill、上下文管理、外部LLM调用及作者确认。上下文续写和一致性检查须在关闭降级的条件下，通过真实MCP Resource与Tool取得资料并用于模型输入。完成普通功能、非功能、智能辅助专项及MCP链路测试，按记录判断功能和流程是否符合设计要求。

任务书要求的主要页面响应时间不超过2秒和多用户并发使用将作为待验证目标，具体页面、测试环境、并发人数及统计口径需在测试设计中明确，不将模型生成耗时直接等同普通页面响应。最终提交完整前后端源码、Skill清单与提示词说明、MCP设计及工具接口、数据库文档和建表脚本、部署说明、测试记录、操作演示及毕业论文。

## （四）拟采用的研究方法或技术方案

研究将采用文献分析、需求分析、系统建模、分模块开发和软件测试相结合的方式。先将任务书要求落实为角色职责、业务流程及数据关系，再按模块开发和联调，并建立需求与测试记录的对应关系。智能辅助评价拟使用具有明确设定的材料，区分正常情节变化和人为设置的冲突，检查续写承接、约束遵循与误报漏报；如进行上下文方案对照，将固定模型及其他主要条件，如实分析结果。

Web部分计划采用Vue 3、Element Plus组织界面，Vue Router管理路由，Pinia管理状态，Axios访问REST接口，ECharts展示创作数据。后端采用Java 17、Spring Boot 3.5.16、Spring MVC和MyBatis-Plus 3.5.17，以MySQL持久化业务数据，使用邮箱注册登录、验证码及JWT落实既定认证流程。Git/GitHub用于版本管理。普通业务按照“Vue—REST接口—Controller—Service—MyBatis-Plus—MySQL”处理，不依赖MCP执行日常保存。

AI部分由Writing Skill确定任务规则，Context Management结合作者要求、当前编辑内容及已有资料选择、裁剪和组合上下文。后端作为Host，MCP Client位于AI模块，MCP Server作为同一Spring Boot应用中的协议适配层；两者通过真实MCP消息与Streamable HTTP通信。Resource表达作品资料，Tool承担参数化查询，其中章节窗口工具用于按位置、数量和长度取得前文章节及已有摘要。Server复用业务Service，不取代原有服务职责，Vue不直接访问MCP Server。

拟执行链路为：浏览器经HTTPS/REST提交任务，后端完成身份与作品权限检查，再由Writing Skill和Context Management发起所需MCP访问；Server经Service及持久化层读取资料，结果沿协议链返回Client和上下文管理。Context Builder与Prompt Builder组织模型输入，外部LLM返回候选，前端展示后由作者确认，再调用普通业务接口保存。作者当前要求和未保存编辑内容可直接进入上下文管理，不要求全部输入绕经MCP。

工程验证将分别记录资源读取、工具调用、上下文采用及错误状态。拟检查跨用户访问、超时和受控降级，授权失败不能通过本地查询绕过。只有真实协议链路通过，才记为MCP接入完成；调用成功不等于生成质量得到提高。具体模型、SDK及编辑器组件将在兼容性与实际条件核验后确定。

## （五）课题预期结论或过程中的特色、创新点

本课题的主要特色拟凝练为以下两项，定位于小说创作场景的应用设计，不将通用框架或普通管理功能作为创新。

1. **面向持续创作的任务化智能辅助。**通过Writing Skill将六类任务的目标、输入、资料需求、模型调用及结果处理组织起来，使辅助操作与当前作品和编辑内容关联。候选内容由作者选择、修改、重新生成或放弃，正式保存以作者确认为前提。作者对生成内容的决定权将贯穿智能辅助流程。

2. **上下文组织与标准化资料访问相结合。**由Context Management确定任务所需信息，利用真实MCP Resource/Tool访问系统已保存的创作资料，再结合当前输入进行裁剪和组合。重点是区分资料访问、上下文组织和模型生成的职责，使同一作品资料能够服务不同辅助任务，而非发明新协议或宣称协议带来质量增益。

预期形成可运行系统及配套设计、实现与测试材料。系统完成后计划通过功能、非功能、智能辅助专项和MCP链路测试，分析主要业务是否符合要求、辅助流程有哪些适用条件及限制。生成质量与一致性检查表现以实际结果为准，不预设提升，也不将尚未验证的方案表述为已取得的创新成果。
