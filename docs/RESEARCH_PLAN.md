## 2. 系统功能与论文研究问题的区别

功能说明回答“用户能做什么”；论文研究问题回答“为什么这样组织、选择了什么方法、有哪些取舍、用什么证据判断方案是否满足需求”。本科设计实现论文可以研究工程问题，无须将每个 CRUD 模块包装成独立算法创新。

| 系统功能举例 | 可研究、可论证的问题 | 应避免的替代写法 |
|---|---|---|
| 作品、章节和设定管理 | 如何围绕用户与作品建立归属和关联，使编辑、统计与 AI 读取使用一致的数据基础？ | “研究新增、删除、修改功能” |
| 六类 Writing Skill | 如何区分任务输入、上下文范围、规则和候选输出，并整合到原有创作操作中？ | “调用六次 API 就是六项创新” |
| MCP 创作资料访问 | 如何把按标识读取资源与按参数查询章节窗口分开，使权限、上下文来源和失败处理可验证？ | “安装 MCP SDK 就是创新”或“MCP 自动理解小说上下文” |
| 上下文续写 | 在给定输入预算下，怎样选择已有资料；相较只提供当前正文，是否更符合既有设定和任务要求？ | 未经测试断言“彻底解决长文本遗忘” |
| 一致性检查 | 如何将已有设定作为检查依据；哪些冲突可以检出，哪些会误报或漏报？ | “LLM 能保证故事逻辑正确” |
| 润色、采用候选结果 | 怎样保留作者决定权，并验证未确认结果不会直接覆盖正式正文？ | 把有确认按钮等同于已证明创作体验改善 |
| 计划、统计、签到和灵石 | 字数、目标达成和奖励如何采用明确口径，避免重复保存造成重复计数或发奖？ | 将积分数量或页面数量当成有效性证据 |
| 拼字房间 | 两种比赛模式的状态与结束条件如何保持一致，排名和奖励能否根据真实记录复核？ | 未选型便宣称已使用 WebSocket 或支持某并发人数 |
| 禅模式与音乐 | 如何把沉浸式交互放入写作流程；已有研究的适用条件是什么？ | 无用户研究就宣称音乐显著提高专注力 |
| 行业创作趋势 | 不同时间、来源与指标的参考信息如何解释，如何避免将局部榜单误称为全行业趋势？ | 把热度等同于作品质量或商业成功预测 |

## 3. 建议研究主线与研究问题

### 3.1 一条主线、三个层次

**研究主线：围绕小说创作工作流，以结构化作品资料为基础，由 Writing Skill 定义任务、Context Management 选择和组织上下文、MCP 标准化访问创作资料与只读工具、LLM 生成或理解文本，形成由作者确认输出的辅助创作系统；以实现证据和可复核测试评价业务完整性、集成可靠性与辅助能力边界。**

- 基础层：创作业务、数据归属、编辑保存、接口和前后端协作，说明完整软件系统如何成立。
- 重点层：Writing Skill、Context Management 与 MCP 的协作，重点验证上下文续写和一致性检查确实通过 MCP 获取资料；分别评价访问正确性、集成可靠性与文本效果。
- 支撑层：计划与可视化、激励与沉浸体验、拼字、行业趋势，说明已确认功能如何与创作流程衔接，以及数据和规则如何验证。

研究重点的分配不改变任何已确认功能的开发范围。支撑层应有实际设计与测试，但不必为每项功能提出独立学术创新。

### 3.2 可回答的研究问题

以下是规划建议，不是已经证实的结论，也不自动成为新增系统功能。

| 编号 | 研究问题 | 方法与证据 | 可得结论边界 |
|---|---|---|---|
| RQ1 | 如何在已确定的前后端分离架构下，组织创作数据、操作流程和权限，使专业写作工具与 AI 辅助形成业务闭环？ | 需求追踪、流程建模、概念/逻辑数据模型、接口与代码检查、端到端场景测试 | 说明本系统方案满足哪些需求；不证明该架构普遍优于所有替代方案 |
| RQ2 | 如何按六类任务组织 Writing Skill；在相同模型与任务条件下，纳入结构化设定的续写是否更符合设定与指令？ | 任务—上下文矩阵、实际模板及调用记录、受控对照、规则检查与人工评价 | 只报告指定模型、材料、预算和评价条件下的观察，不宣称基础模型能力提升 |
| RQ3 | 基于既有小说资料的一致性检查能够发现哪些潜在冲突，其误报、漏报和适用边界是什么？ | 带已知冲突及无冲突对照的测试材料、逐项标注、输出与依据对齐、错误分类 | 报告局部检出能力，不保证整部长篇叙事逻辑正确 |
| RQ4 | 如何使保存、统计、目标达成、签到奖励、兑换与拼字结算的数据和状态保持一致，并保留作者对 AI 输出的控制？ | 状态与事务设计、数据核对、重复/并发/失败路径测试、候选采用流程检查 | 证明被测试的工程行为；不能据此声称用户长期留存或写作质量提高 |
| RQ5 | 如何在单体 Spring MVC 系统中以 MCP 连接 Skill 所需的创作资源与只读查询，同时保持权限隔离、上下文契约和故障降级的正确性？ | 官方规范对照、Resource/Tool 契约、真实协议链路、权限与故障注入测试、脱敏追踪 | 证明本系统在指定环境下完成可靠集成；不研究协议底层实现，不将 MCP 本身等同于文本质量提升 |

行业趋势的来源可信度、音乐与激励的设计依据纳入 RQ1/RQ4 的支撑分析。是否需要独立用户体验研究，待条件明确后决定；当前不增加强制的人体参与实验。

### 3.3 可表述的贡献类型

适合定位为：面向具体创作场景的系统设计、结构化数据与任务调用的整合、MCP 访问契约及工程验证、作者确认机制。Writing Skill 是本项目的任务组织概念；现有 Wordcraft、Re3、DOC 可用于比较相关机制，不能声称六类 Skill 分类是首次提出，也不宣称创造了新的 MCP 协议。

不得预写“首次提出”“国内首个”“显著提升效率”“优于现有系统”。文献不足不是不存在先前工作的证明；测试不支持改善时，应如实报告没有观察到改善或存在退化。

D2 检索可能遇到 RAG、知识图谱或训练方法，可作为相关工作和方案边界阅读；**阅读某技术不构成采用该技术的需求决定**。D8 的协议比较也仅服务后续详细设计。

### 4.1 v1.4 增量方向及分工

保留 D1—D9 编号，新增 **D10：MCP 标准化上下文与工具访问集成**，服务 RQ5。研究目的为确定协议能力与应用职责的映射、只读契约、权限、故障恢复及验收证据，不研究协议编码或底层实现。

- 中文：模型上下文协议、资源访问、工具调用、上下文集成、权限隔离、故障降级；组合：`("模型上下文协议" OR MCP) AND (资源 OR 工具调用 OR 上下文)`；`MCP AND (权限 OR 安全 OR 集成测试 OR 故障降级)`。
- 英文：Model Context Protocol, resources, tool invocation, context integration, authorization, failure handling；组合：`"Model Context Protocol" AND (resources OR tools OR integration)`；`"Model Context Protocol" AND (security OR authorization OR evaluation OR testing)`。
- D2 扩展资料来源、版本及截断标识，但选择、排序和预算仍归 Context Builder；D3 扩展 Skill 的确定性调用编排，不把 Skill 等同于 MCP Prompt。
- D5 扩展 MCP/REST 两类适配入口与共用 Service 的边界；D6 扩展真实协议链路、契约及异常测试。D8 继续研究奖励与比赛状态，不因 MCP 而变更同步协议。
- D1、D4、D7、D9 原有问题保留；MCP 不替代作者控制、叙事一致性算法、沉浸体验或数据来源核验。

## 6. 论述与证据的分工

### 6.1 必须有真实外部证据的论述

- 创作者普遍存在何种困难、人机协同写作的已有发现：需要相关实证研究；未做需求访谈时不能编造访谈人数、原话和比例。
- LLM 的长文本利用、叙事连贯性与一致性限制：需要对应任务研究，不能由通用事实问答结果直接推导。
- 提示组织、摘要、上下文选择的既有方法：需要原始研究或权威来源；引用不等于本系统已采用或复现。
- 音乐、游戏化、目标反馈是否影响专注、动机或产出：需要研究设计与对象相符的证据，同时记录反例及条件差异。
- 行业规模、平台排名、题材热度和趋势变化：需要可追溯数据与统计口径，不使用模型生成的数字。
- “现有方法的不足”“研究空白”“优于同类产品”：需要有范围记录的检索和比较；不足以核实时改为研究动机或待检验问题。

### 6.2 必须由本系统材料支撑的论述

| 拟论述内容 | 所需本系统证据 |
|---|---|
| 功能覆盖和角色权限 | 基线条目—需求—接口/代码—测试用例追踪表，实际操作结果 |
| 数据归属、实体关系与保存策略 | 实际表结构、约束、Service 逻辑、事务与异常测试 |
| 六类 Skill 的差异 | 实际任务输入、上下文选择规则、模板版本、调用链及脱敏记录 |
| 作者确认、候选采用与原文保护 | 页面交互、接口写入条件、采用/拒绝/失败的实际测试 |
| 字数、时长、连续天数、目标完成率 | 先定义计数规则，再以已知输入和原始记录复算；截图只辅助展示 |
| 灵石余额、流水与权益一致性 | 获得/消耗/重复请求/异常中断后的余额与流水核对 |
| 拼字排名、结束与奖励正确性 | 两种模式的时间和字数记录、状态变化、结算结果与边界测试 |
| 趋势展示与 Skill 联动 | 实际采用的数据来源和日期、转换口径、展示结果；联动仅按最终实现描述 |
| 性能、可靠性与部署可复现性 | 环境、数据规模、负载、测量方法、原始结果、实际部署配置与运行记录 |
| AI 辅助效果 | 已固定的对照条件、评测材料、评分规则、逐次输出及分析；不能借用他人实验充当本系统结果 |

### 6.3 两类证据共同支撑的内容

方法选择用文献解释候选方案及取舍，再用实际实现说明本系统采用方式，最后由测试说明结果。不能用“Spring Boot 官方文档”证明本系统高性能，也不能用单张成功截图证明 LLM 在一般情况下有效。

需求文件能够证明“要求实现”，不能证明“已经实现”或“用户体验已改善”。当前没有实测数据，所以所有提升率、准确率、并发容量、用户满意度和业务统计均为 **待实测**。

## 7. 后续验证设计建议

本节只规划取证方法，不启动实验、不调用外部模型、不新增产品功能。样本数量、调用次数和评价人员在评测方案阶段据时间、预算与材料条件确定并记录，不预填结果。

### 7.1 工程验证

以正式需求形成测试矩阵，覆盖正常、边界和失败路径。重点关注：跨用户/作品访问、保存失败与章节切换、版本恢复、导入导出内容核对、统计重复累计、签到重复提交、兑换失败、拼字结束与重复结算、AI 调用失败以及未确认内容不得写入正文。

字数须区分“现存正文长度”“新增创作量”“比赛期间新增量”；删除、粘贴、导入、恢复版本、AI 采用是否计入不同指标，均需后续明确。签到连续天数与连续创作天数不能混用。测试这些规则属于验证现有需求，不等于已确定规则。

性能测试先固定机器、浏览器、数据库规模与并发操作，再报告响应时间、错误和资源使用；将本地业务耗时与外部 LLM 耗时分开。房间人数上限依基线要求由性能验证后确定。

### 7.2 Writing Skill 与续写评价

1. 六类 Skill 均验证输入、上下文选择和输出流程；效果比较优先深入上下文续写，不要求为六类任务各写一篇算法实验。
2. 建议对照 A：当前章节正文与相同作者指令；B：A 加入本系统选择的结构化资料及已实现上下文。对照仅用于评测，不增加面向用户的功能开关。
3. 控制模型与版本、参数、任务、输出预算、采样次数；记录实际输入长度和资料范围。若 B 输入更长，须说明上下文内容与长度的混杂，不能把差异全部归因于组织算法。
4. 先约定设定遵循、任务遵循、局部连贯和可采用程度的评分依据，再进行评价；保留完整输出和失败例。条件允许时打乱方案标签，记录评价者及分歧处理。
5. 使用自编或获准材料，覆盖多个设定与任务，区分开发调试材料和最终测试材料；报告有限样本和模型非确定性，不选择性展示最佳输出。
6. 不将另一个 LLM 的评分当作唯一真值；若仅有作者自评，明确自评偏差，不伪称独立盲评或多人一致评价。

### 7.3 一致性检查评价

构造已知事实的测试材料，包含人物、关系、地点、能力、物品时间及已发生剧情等基线检查方向；每个案例注明依据、预期冲突与可接受解释。加入无冲突案例，以及“有明确变化依据”的情节，防止把正常人物成长或状态变化误判为矛盾。

先确定按“案例”还是“冲突条目”计数，定义输出与人工标注的匹配、重复提示和部分匹配规则，再计算精确率、召回率及必要的 F1，同时报告原始 TP、FP、FN 和实际样本数；分母为零时标记不适用。保留误报、漏报及依据不足的结果。

若上下文未包含某关键事实，应记录为上下文缺失，不能把全部失败归结于模型推理。使用人工植入冲突只能说明这些测试条件下的检测表现，不能代表真实长篇小说全部问题。

### 7.4 支撑模块的结论限制

激励与音乐当前以功能、状态和交互验证为主，不预设长期行为效果实验。行业趋势以来源可追溯、指标转换正确和显示真实数据为主，不进行市场预测。测试用虚构故事可以作为明确标注的测试材料，但不能冒充真实用户稿件、行业数据或已经发生的实验结果。

### 7.5 MCP 集成验证与验收证据

下列均为待执行测试；工程骨架 Maven 构建成功不能替代 MCP 验收。

| 测试层次 | 场景与预期 | 应保留证据 |
|---|---|---|
| 契约 | URI、参数、返回字段、空结果、长度上限、截断及摘要有效性符合约定；未知资源或非法参数有明确错误 | 契约样例、输入输出、断言结果 |
| 协议集成 | 完成初始化、能力协商，真实 resources/read 和 tools/call 返回可解析数据 | SDK/协议版本、请求关联号、脱敏协议记录 |
| 核心 Skill | 关闭降级测试续写与一致性检查，两者都使用 Resource 和 Tool 的返回数据；修改人物设定后 ContextBundle 可观察到变化 | 来源标识、上下文快照摘要、调用链及断言；不能只展示工具演示页 |
| 上下文边界 | 首章无前文、可选资料缺失、旧摘要、超长输入、未保存正文；区分事实与大纲计划，不把空资料编造为事实 | 选取/排除原因、预算、缺失和截断标识 |
| 权限与安全 | 两作者并发访问不串会话；跨作品/章节、过期或错误凭据、错误受众/权限、伪造身份被拒绝；不因本机访问跳过鉴权 | 拒绝结果、无越权内容断言、日志脱敏检查 |
| 故障与恢复 | 超时或临时5xx按基线最多重试一次，再通过本地适配器重建完整上下文；恢复后真实 MCP 链路可用 | 故障注入、尝试次数、分支记录、契约一致性比对 |
| 禁止降级 | 401/403、跨用户/作品访问或身份非法立即停止；本地数据访问也失败则报告 AI 失败 | 未调用本地越权替代路径、未调用模型的断言 |
| 原文保护 | 查询无业务写入，生成失败、拒绝候选不覆盖正文，只有作者确认后的正常 REST 写流程可保存 | 调用前后数据对比、采用/拒绝测试 |
| 可观测与性能 | 分开测量 MCP、Context Builder 和外部 LLM 耗时，记录并发量、成功率及失败类型 | 环境、原始耗时、错误计数；无预填提升率 |

可先用固定模型响应验证工程链路，再用真实模型完成第7.2—7.3节有限材料评价，并标清两种测试。MCP 与本地适配器可做等价读取测试，但不增加面向用户的技术开关。MCP 的价值主要从标准访问、职责边界和可追踪性论证，不以有/无 MCP 的文本评分差异直接证明模型质量提升。

采用有检索记录和筛选理由的专题文献调研，不将其标成已经完成的系统性综述或元分析。已有候选记录继续复用，下列阶段仍是后续工作的门槛。

| 阶段 | 具体工作 | 建议产物 | 进入下一阶段的必要条件 |

### 11.1 基线方案如何转化为论文论证

| 要点 | 本系统定位与边界 | 论文需回答和取证的内容 |
|---|---|---|
| 部署集成 | Spring Boot 后端 AI 编排层作为 Host，内部持有 Client；Server 为同一应用/JVM的协议适配层。以 Streamable HTTP 本机回环访问 `/internal/mcp`，不拆微服务 | 展示部署与调用图、协议握手、线程与会话隔离及兼容配置；同进程部署不等于直接方法调用冒充 MCP |
| Resource | `novel://works/{workId}/` 下的 overview、characters、relationships、world、outline、chapters/{chapterId}、summaries/{chapterId}，仅读取已存在且可用资料 | 解释按标识读取的语义、作品归属、内容来源与更新时间；不得要求自动摘要生成或新数据库表 |
| Tool | `get_chapter_window(workId, anchorChapterId, previousCount, includeExistingSummaries, maxChars)`，按参数返回有界前文章节/有效摘要 | 与 Resource 的区别在参数化查询，不在是否写入；Tool 也可以只读。返回缺失、截断与来源信息，不读取未来章节，不做向量检索 |
| Writing Skill | 六类任务保持；由确定性后端编排选择所需 Resource 与 Tool，通过 Client 调用。续写、一致性检查必须真实参与；纯选中文本润色可不额外读取 | 任务—来源矩阵、实际调用及输出用途；不增加自主 Agent，不把 Skill 强制改造为 MCP Prompts |
| Context Management | Context Builder 决定选取、排序、去重和预算，合并未保存正文及 MCP 返回资料 | 访问机制与内容组织策略分工；MCP 不负责自动记忆、相关性选择或令牌预算，也不替代原上下文机制 |
| REST / Service | Vue 的业务 CRUD 与确认写入继续走 REST；MCP 是 AI 只读入口；二者复用 Service 的归属校验和数据逻辑，Mapper 执行数据库访问 | 防止双份业务规则和重复数据；Server 不反调 Skill/Context Builder，避免递归调用 |
| 降级 | 只读临时故障按基线重试后改用本地适配器调用同一授权 Service，重建整个 ContextBundle，不混合半份结果 | 区分协议/网络故障与鉴权失败；鉴权失败禁止降级，核心资料不足不得无提示继续生成；协议不兼容即使本地成功也不算 MCP 验收通过 |
| 安全 | 内部入口不公开代理；短期只读凭据绑定用户、作品、受众和权限，每次校验；session不等于授权；校验 Origin，正文按资料而非高优先级指令处理 | 内部身份方案是本系统应用约束，不能宣称已实现通用第三方 OAuth 授权生态；不透传令牌到外部模型、不信任模型给出的 userId |
| 调用追踪 | 请求关联号、Skill、资源/工具标识、耗时、错误、是否降级及上下文来源 | 可复现故障与数据流，不记录完整稿件、JWT或密钥；不为追踪强制增加复杂平台或数据表 |

完整正常流程：Vue 提交任务与未保存正文 → 后端认证及作品授权 → Skill 确定资料需求 → Context Builder 经 MCP 访问适配器和 Client → 初始化/协商后的真实 Resource 读取与 Tool 调用 → 同应用 Server 校验权限、调用 Service/Mapper → 返回有界创作资料 → Context Builder 组织 ContextBundle → Skill 组合指令 → LLM → 候选展示 → 作者确认后走业务保存接口。故障处理发生在上下文获取阶段，模型错误单独处理。

### 13.2 研究与验证要求同步

- 保留六类Writing Skill及LLM + Writing Skill + Context Management + MCP主线。任务书四类示例由六类覆盖，“等技能”不是封闭清单。
- MCP是工程协议边界：后端Client经真实transport访问同应用Server，Server复用创作查询Service；资源用Resource，带参数的章节窗口查询用 `get_chapter_window` Tool。不研究协议底层，不增加自主Agent或Multi-Agent。
- Context Management按任务选择、裁剪、组合上下文；作者要求、选中文本和未保存编辑内容可直接来自请求，系统已存资料按需经MCP取得。不把全部LLM输入强制绕经MCP。
- 作者决定采用、修改、重新生成或放弃候选；正式稿件经普通业务接口保存，不以MCP写入Tool自动覆盖正文。
- 上下文续写与一致性检查必须在关闭fallback的验收条件下实际调用Resource和Tool，并证实返回资料进入上下文。降级单独测试，不能用降级成功替代MCP接入证据。
- TXT整本单章节与规则自动分章两种导入均必做；上传解析后先预览、检查/调整、确认，再进入统一作品/卷章节模型。保留导出，不新增DOCX/PDF/EPUB导入或独立TXT数据系统。
- 原件还明确要求富文本编辑、素材管理、灵感速记、章节版本、生成结果人工编辑与重新生成、主要页面响应≤2秒、多用户并发及使用验证，不能因用户摘要未逐项列出而遗漏。≤2秒是需求，不是测试结论；并发人数、页面清单和测量条件尚须明确。
- 维持四项可行性及性能、安全性、可靠性三项非功能分类；不增加未确认技术栈。MCP集成正确性、上下文组织、生成质量分别评价，不以MCP调用成功证明生成质量改善。
