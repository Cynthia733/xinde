# 2 关键技术研究

## 2.1 前端相关技术

本系统面向小说创作者，采用PC网页优先的前后端分离方式。前端负责页面展示与用户交互，并组织页面导航、共享数据、接口请求和个人创作数据展示。系统拟以HTML5、CSS3和JavaScript为基础，使用Vue 3构建前端应用，结合界面组件、路由、状态管理及图表工具，为作品管理、正文编辑和智能辅助提供操作界面。

### 2.1.1 HTML5、CSS3与JavaScript

本系统前端以HTML5、CSS3和JavaScript作为基础，分别用于页面结构、布局样式和交互处理。HTML5用于组织导航、表单、正文区域和资料面板，使章节目录、编辑内容与操作入口在页面中具有明确位置。结合长文本写作需要，编辑页面以正文区域为主体，工作台和创作资料页面则分别组织进度信息、资料列表与编辑表单。

CSS3主要用于设置布局、字体、间距及操作状态的显示样式。例如，正文编辑页面需要协调章节目录、编辑区和辅助面板的宽度，人物与世界观页面需要清楚呈现资料列表和输入区域。JavaScript负责响应输入、点击和文本选中等操作，并处理相应的页面数据变化，也是Vue前端开发的语言基础。三者共同完成页面内容的组织、显示和交互，为后续组件开发提供基础。

### 2.1.2 Vue 3

Vue 3是用于构建用户界面的JavaScript框架，支持组件化开发和响应式数据更新。组件化方式可以将页面拆分为相对独立的部分，响应式机制则根据数据变化更新相关界面。[Vue官方指南](https://vuejs.org/guide/introduction.html)本系统拟使用Vue 3构建单页应用，组织创作者在工作台、作品资料和章节编辑之间的操作，并呈现加载、编辑、保存和等待辅助结果等页面状态。

小说创作页面包含多个相互配合的区域，适合按用途划分组件。例如，章节目录用于选择编辑对象，正文区域用于显示和编辑内容，AI辅助面板用于提交要求和展示候选。组件之间通过传递数据和响应操作保持联系，重复使用的表单与提示界面可以统一维护。当前章节、请求状态和返回结果发生变化时，相应区域随之更新，保存提示根据后端返回结果显示。

Vue Router与Pinia分别配合Vue完成页面导航和必要的数据共享，共同组织前端应用。已有Web系统设计案例采用Vue构建单页前端，并结合界面组件与后端接口完成业务交互[P11]。该案例为前端应用组织提供参考，本系统则结合小说创作需求选用Vue 3，并围绕章节编辑和资料管理安排页面与组件。

### 2.1.3 Element Plus

Element Plus是适用于Vue 3的前端组件库，提供表单、按钮、菜单、表格、对话框、分页和消息提示等常用组件。[Element Plus组件目录](https://element-plus.org/en-US/component/overview.html)本系统的认证、资料录入和管理页面需要反复使用这些控件，因此选用Element Plus组织通用界面，使同类操作采用一致的呈现方式。

在本系统中，邮箱注册和登录页面可使用表单组织输入与提示，作品、人物和世界观管理可结合列表与对话框完成资料查看和编辑，轻量管理员页面可使用表格及分页展示管理对象。这些页面虽然处理的数据不同，但具有相近的录入、查询和修改操作，采用统一组件便于复用界面写法和提示方式。小说正文编辑区域则根据长文本与富文本创作需要单独设计，并与周围的目录和操作控件配合使用。

### 2.1.4 Vue Router与Pinia

Vue Router用于管理单页应用的路由，通过配置建立页面地址与组件的对应关系，并提供导航控制能力。[Vue Router指南](https://router.vuejs.org/guide/)及[导航守卫说明](https://router.vuejs.org/guide/advanced/navigation-guards.html)本系统拟用它组织登录、工作台、作品管理、章节编辑、创作资料、统计和管理员等页面，使用户能够围绕当前作品进入相应操作界面。

前端可结合登录状态和用户角色安排页面入口，实际请求的JWT认证和接口访问权限仍由后端校验。路由主要处理用户进入哪个页面，页面之间共同使用的数据则交由Pinia管理，两者分别服务于导航和状态共享。

Pinia用于管理多个组件共同使用的数据状态。[Pinia官方说明](https://pinia.vuejs.org/introduction.html)本系统可将当前用户基础信息、当前作品和章节标识以及必要的全局界面状态纳入共享管理。例如，切换章节时，目录与编辑区域需要使用同一章节标识；切换作品时，相关资料页面也需要对应当前作品。通过集中管理这些信息，各组件可以读取一致的当前选择，并在用户操作后更新相应显示。

### 2.1.5 Axios

Axios是用于发送HTTP请求和接收响应的客户端工具，支持统一请求配置及请求、响应拦截。[Axios官方仓库文档](https://github.com/axios/axios#interceptors)本系统采用前后端分离方式，Vue页面中的业务操作需要通过接口提交给Spring Boot后端，因此拟使用Axios处理注册登录、作品与章节管理、创作资料保存、AI辅助请求和统计查询等通信。

通过统一配置接口基础地址和公共请求信息，页面可以按业务需要提交参数并处理返回数据。请求与响应拦截可用于组织认证信息及通用提示，页面再根据返回结果显示数据、保存状态或错误信息。需要认证的请求携带相应凭证，由后端完成身份和权限校验。AI辅助请求也先进入本系统后端，再由后端调用模型服务，模型服务密钥由后端管理，不直接放在前端。

### 2.1.6 ECharts

ECharts是数据可视化图表库，提供折线图和柱状图等形式，可通过坐标轴、数据系列和数值提示展示统计结果。[ECharts折线图说明](https://echarts.apache.org/handbook/en/how-to/chart-types/line/basic-line/)与[柱状图说明](https://echarts.apache.org/handbook/en/how-to/chart-types/bar/basic-bar/)本系统的创作统计与分析页面需要呈现个人字数变化、作品进度和AI辅助使用情况，选用ECharts绘制其中的趋势和数量图表。

系统拟使用折线图展示近7天或近30天每日实际新增创作字数，以便查看个人字数随日期的变化；使用柱状图展示各作品当前字数、章节数量及六类Writing Skill的使用次数。作品情况支持全部作品或指定作品筛选，近7天和近30天选择用于个人字数趋势。不同形式的图表分别对应时间变化和数量展示，便于作者查看相应创作信息。

数据总览可使用统计卡片，写作计划完成情况可使用进度条，活跃情况和候选采纳数据按内容选择合适的展示方式。相关数据均来源于当前创作者在本系统中的真实业务记录，由后端完成统计后返回前端，ECharts承担其中的图表展示工作。

### 2.1.7 前端技术选型

本系统面向PC网页端的小说持续创作，页面既要组织作品和设定资料，也要协调章节目录、正文编辑区与AI辅助面板。技术选型主要考虑组件划分、交互状态管理以及与现有开发准备的衔接。Vue 3、React和Angular均可用于构建此类交互界面，比较重点在于各自的页面组织方式和本项目采用时需要配合的技术。

Vue 3通过声明式模板和响应式数据组织界面，单文件组件可集中描述组件的结构、逻辑和样式。[Vue官方指南](https://vuejs.org/guide/introduction.html)React以组件组织界面，常用JSX表达页面结构，并通过状态更新和组件间数据传递协调交互。[React快速入门](https://react.dev/learn)Angular以组件类和模板组织页面，可使用Signals管理状态，并提供路由、表单等配套能力。[Angular组件说明](https://angular.dev/essentials/components)、[状态管理说明](https://angular.dev/essentials/signals)及[框架概览](https://angular.dev/overview)三种方案都能够支持页面拆分与数据驱动的交互，选择时还需结合项目已有准备和实际组织需求。

本项目已围绕Vue开展前期技术学习和页面方案梳理，并确定Element Plus、Vue Router和Pinia的组合。采用Vue 3可沿用这些准备：按业务划分工作台与资料页面，在编辑页面中协调章节选择、正文和候选结果，通过路由组织页面入口，通过共享状态保持当前作品与章节信息一致。React和Angular也可实现这些需求，但改用其他方案需要重新安排配套组件和应用组织方式。结合本项目规模与开发准备，继续采用Vue 3更符合当前实施安排。

通用表单和列表拟使用Element Plus，正文编辑区域另按创作需要选择组件。Axios用于前后端HTTP通信，ECharts用于个人创作字数和作品情况等折线图、柱状图展示。这些工具分别配合界面、通信与可视化需求，共同组成当前前端方案，而非作为框架性能优劣的判断依据。

## 2.2 后端相关技术

本系统后端负责接收前端请求、处理业务逻辑和访问数据库，为用户认证、作品与章节管理、创作资料管理及智能创作辅助提供服务。本系统后端基于Java 17进行开发，以Spring Boot组织应用，结合Spring MVC处理接口请求，使用MyBatis-Plus完成常用数据访问。JWT用于身份认证，Swagger/Knife4j拟用于接口文档与开发调试，各项技术共同服务于前后端之间的业务交互。

### 2.2.1 Spring Boot

Spring Boot是在Spring基础上用于组织和运行应用的开发框架。其自动配置会根据项目依赖及相关配置提供常用组件的默认设置，开发者也可以按应用需要进行调整。Starter将某类功能常用的依赖集中组织，减少项目初始化时逐项选择组件的工作。[Spring Boot自动配置说明](https://docs.spring.io/spring-boot/3.5/reference/using/auto-configuration.html)

当前工程采用Spring Boot 3.5.16，并引入Web及MyBatis-Plus相关依赖。本系统包含认证、作品与卷章节、创作资料、写作计划和个人创作统计等业务，也需要为智能辅助与轻量管理员提供接口。采用Spring Boot作为后端基础框架，可在同一应用中组织这些业务，配合配置文件管理运行参数，并通过Maven统一管理依赖。Web请求处理与数据访问分别由相应组件承担，业务服务负责连接具体操作与数据处理。

已有学生德育量化考核系统采用Spring Boot、MyBatis与Vue完成Web应用的设计与实现，为前后端分离系统的工程组织提供了案例参考[P11]。本系统结合小说创作需求选择上述框架，拟按业务划分服务，并统一安排接口响应和异常处理，使前端能够根据返回信息展示数据及操作状态。

### 2.2.2 Spring MVC

Spring MVC是Spring体系中基于Servlet的Web框架，主要处理HTTP请求与响应。[Spring MVC官方说明](https://docs.spring.io/spring-framework/reference/web/webmvc.html)在Spring Boot组织的后端应用中，它负责将请求分配到相应的控制器，并完成参数接收和结果返回。本系统采用前后端分离方式，页面展示由Vue负责，后端主要通过接口交换业务数据，因此拟使用Spring MVC构建Web接口层。

系统接口围绕作品、章节和创作资料等业务对象进行RESTful设计，结合请求方式表达查询、保存和修改等操作。前端提交请求后，Controller接收参数并调用相应的Service，由业务服务处理具体规则，再将结果以统一的JSON结构返回。例如，章节保存需要处理正文与所属作品的关系，智能辅助请求需要进入相应任务流程，这些业务处理由服务层承担。

统一响应与全局异常处理用于协调接口返回方式，使前端可以区分业务数据、操作提示和异常信息。注册登录、作品查询及正文保存等页面由此使用一致的接口交互方式，同时保留各项业务自身的处理要求。

### 2.2.3 MyBatis-Plus

MyBatis-Plus是在MyBatis基础上提供常用数据访问能力的持久层工具，支持基础增删改查、条件构造和分页等功能。开发者可以通过Mapper组织数据访问，并按需要扩展查询逻辑。[MyBatis-Plus官方介绍](https://baomidou.com/introduce/)对于多种业务对象反复使用的基础操作，这种方式可以减少重复编写相近的数据访问代码。

当前工程采用MyBatis-Plus 3.5.17，引入适用于Spring Boot 3的Starter。本系统需要持久化用户、作品、卷章节及人物、世界观和大纲等资料，也需要保存写作计划和AI辅助相关业务记录。这些对象具有较多查询与维护操作，因此拟使用MyBatis-Plus连接业务服务与MySQL，将数据访问集中到相应Mapper中。

作品列表和章节列表可结合条件查询与分页组织返回数据，业务服务则负责确定当前用户及作品范围，避免将访问范围直接交由前端决定。涉及多类记录汇总的创作统计，可按实际需求编写专门查询。具体数据结构将在数据库设计中确定，分页等能力也需结合工程配置使用。

### 2.2.4 JWT身份认证

JWT是一种用于在通信双方之间传递声明的令牌格式，可用于前后端分离系统中的身份认证。本系统拟采用的签名JWT通常由Header、Payload和Signature三部分组成，分别记录令牌信息、声明内容和签名。后端通过验证签名检查令牌的完整性和来源，Payload本身通常经过编码而非加密。[RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html)

本系统采用邮箱账号体系，拟在用户通过邮箱和密码认证后由后端签发JWT，前端在后续请求中携带认证凭证。后端校验令牌及有效期，识别当前用户，并结合角色和业务规则检查操作权限。例如，创作者访问作品与章节时需要核对数据归属，管理员接口则根据对应角色限制访问。邮箱验证码用于注册验证和密码找回等流程，与登录后的接口身份校验共同构成认证过程。

登录状态保持、主动退出及令牌生命周期将结合认证流程统一设计，前端根据后端认证结果呈现相应操作状态。

### 2.2.5 Swagger/Knife4j

OpenAPI用于描述HTTP接口，Swagger相关工具围绕接口描述提供文档等支持，Knife4j则提供接口文档展示与调试界面。[OpenAPI说明](https://swagger.io/docs/specification/v3_0/about/)及[Knife4j官方文档](https://doc.xiaominfo.com/docs/quick-start)前后端分离开发需要明确请求地址、请求方式、参数、返回结构和认证要求，接口文档可作为双方核对调用方式的依据。

本系统拟采用Swagger/Knife4j整理后端接口文档，配合作品管理、章节编辑及智能辅助等功能的开发。前端可根据文档组织请求，开发过程中也可通过调试界面查看参数与响应，定位接口调用问题。文档内容应随接口调整同步维护，并与后续功能测试相互配合。当前该工具属于技术方案，尚未加入工程依赖，本节仅说明其用途。

### 2.2.6 后端技术选型

本系统后端基于Java 17，采用单体Web应用组织常规创作业务与智能辅助服务。用户认证、资料维护和章节保存需要稳定的请求处理与数据访问分工，因此选用Spring Boot与Spring MVC配合构建后端。Spring Boot通过自动配置组织常用组件，Spring MVC承担Web请求处理，两者共同服务于面向前端的RESTful接口。[Spring Boot自动配置说明](https://docs.spring.io/spring-boot/3.5/reference/using/auto-configuration.html)及[Spring MVC文档](https://docs.spring.io/spring-framework/reference/web/webmvc.html)当前工程采用Spring Boot 3.5.16，沿用该基础可将业务服务与AI辅助入口放在同一应用中维护，符合本项目现有部署和模块组织要求。

持久层主要考虑基础数据操作与自定义查询之间的配合。MyBatis围绕SQL映射组织数据访问，允许通过XML或注解配置查询及结果映射；MyBatis-Plus建立在MyBatis基础上，补充通用CRUD、条件构造与分页等能力，同时保留自定义查询方式。[MyBatis介绍](https://mybatis.org/mybatis-3/)及[MyBatis-Plus介绍](https://baomidou.com/en/introduce/)JPA是Java持久化规范，Hibernate是其常见实现之一，以实体及其关系映射组织持久化，也支持查询语言、条件查询和原生SQL。[Jakarta Persistence规范](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2)及[Hibernate ORM说明](https://hibernate.org/orm/)二者体现了不同的数据访问组织方式，不能仅凭采用哪一种就判断查询性能。

本系统的作品、卷章节和创作资料具有较多常规增删改查，个人创作统计与上下文取材又需要按业务组合查询条件。相比主要逐项编写SQL映射，MyBatis-Plus提供的基础操作更贴合这些重复的数据维护需求；相较以实体关系管理为中心的方案，本项目更倾向保留按业务编写查询的方式。因此选择当前工程中的MyBatis-Plus 3.5.17，在使用基础操作的同时，为统计和上下文查询保留专门处理。已有Web工程采用Spring Boot与MyBatis完成业务系统开发[P11]，可作为技术组合的应用参考，本项目选用增强工具则依据自身的数据访问需求。

身份认证方面，Session通常由服务端维护会话信息，客户端通过会话标识关联后续请求；签名JWT则在令牌中携带声明，由后端校验后识别请求身份。[HttpSession文档](https://jakarta.ee/specifications/servlet/6.0/apidocs/jakarta.servlet/jakarta/servlet/http/httpsession)及[RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html)两种方式都可用于Web认证，前后端分离本身并不排除Session。本系统沿用已确定的JWT方案，将邮箱密码认证后的身份凭证用于接口请求，并结合角色、数据归属和业务规则校验权限。这一选择与当前认证设计一致，不预设其安全性或性能优于Session。

接口协作方面，后续拟结合OpenAPI/Swagger相关描述能力与Knife4j整理请求参数、返回结构和认证要求，供前后端核对与开发调试使用。[Knife4j官方文档](https://doc.xiaominfo.com/docs/quick-start)该部分目前属于技术方案，尚未加入工程依赖。

## 2.3 数据库技术

### 2.3.1 MySQL

MySQL是一种关系型数据库管理系统，以表组织数据，通过行和列描述具体记录及其属性，并使用SQL完成数据查询与维护。不同业务对象可以分别存储，再通过关联关系共同表达业务内容。[MySQL官方介绍](https://dev.mysql.com/doc/refman/8.4/en/what-is-mysql.html)本系统中的用户、作品、卷与章节具有明确的归属关系，人物和世界观等资料也需要与作品关联，采用关系型数据库便于按这些联系组织和查询创作数据。

在数据管理方面，主键用于唯一标识记录，外键约束可用于维护关联数据的引用完整性。MySQL的InnoDB存储引擎支持外键及事务提交、回滚等能力，可为涉及多项数据变更的操作提供事务支持。[InnoDB官方说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html)索引则可用于支持条件查找和关联查询，其设计需要结合查询方式与数据特点确定。[MySQL索引说明](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html)这些能力为创作资料维护提供了数据库层面的支持，具体约束与事务范围仍需结合业务设计。

本系统计划使用MySQL保存用户账号、作品与卷章节、人物设定及关系、世界观和大纲，并记录写作计划与AI辅助相关业务。后端拟通过Spring Boot和MyBatis-Plus组织数据访问，将业务处理与持久化操作衔接起来。选择MySQL既考虑了创作数据之间的关联，也与当前Java后端技术组合保持一致。创作统计所需数据同样来自系统业务记录，由后端按当前登录创作者的范围查询和汇总，为个人创作进度、活跃情况与AI辅助使用情况提供数据。具体数据表、关联约束和统计口径将在第4章数据库设计中展开。

## 2.4 大语言模型相关技术

本系统拟将大语言模型的文本处理能力与小说创作业务结合，通过Writing Skill组织辅助任务，通过Context Management准备任务所需的创作背景。模型负责生成候选内容或检查结果，作者负责判断和确认；系统中已保存资料的访问则与MCP协议链路衔接。

### 2.4.1 大语言模型

大语言模型（Large Language Model，LLM）是一类通过大量数据训练的语言模型，能够学习文本中的语言规律，并根据输入上下文处理和生成文本。现有模型广泛采用Transformer架构，其中自回归生成模型根据已有内容逐步预测后续文本，可用于问答、内容生成和改写等任务[P01]。对于小说创作，这种能力可以提供表达和构思上的候选，而具体任务仍需要明确的要求与相关故事资料。

已有研究将模型嵌入故事编辑工具，通过预设与自定义操作支持续写、扩展和改写，体现了语言模型参与作者写作过程的一种方式[P13]。本系统拟调用外部LLM，为大纲规划、人物塑造和情节构思提供建议，为上下文续写、文本润色提供候选文本，并辅助分析一致性问题。这六项任务是本项目围绕创作流程确定的分类，模型承担其中的文本生成与分析工作。

小说内容随着章节推进不断积累，人物经历、事件顺序和世界规则之间存在较长距离的联系。长故事研究区分了局部表达流畅与整体内容一致，并分析了人物、时间和世界设定等方面的矛盾[P15]。本系统因此需要围绕当前任务组织输入，而非仅依赖模型记住此前所有内容。对于故事中的合理新增情节，应结合作者意图与既定设定判断，不能直接作为生成错误。

本系统将LLM定位为辅助工具，模型返回的建议、文本和检查提示均供作者参考。作者可以采用、修改、重新生成或放弃，确认后的内容再通过正常业务流程保存。这样的使用方式将生成与正式稿件管理分开，使最终内容的决定权保留在作者手中。

### 2.4.2 Writing Skill

Writing Skill是本系统用于组织小说智能创作任务的应用层设计。不同任务需要处理的文本范围、创作要求和返回内容并不相同，将其分别组织有助于明确一次辅助操作要完成什么。系统拟为各项Skill安排输入要求、资料需求、任务指令、输出形式与结果处理，使作者能够通过相应入口提交要求，而不必每次重新说明全部任务背景。

提示学习研究讨论了通过任务描述、示例及模板表达任务要求的方式[P05]；Wordcraft也将预设操作和作者自定义要求结合到故事编辑过程中[P13]。这些研究为任务表达和交互组织提供了参考。本系统的Writing Skill则面向后端业务编排，负责连接作者输入、上下文准备、模型调用与候选处理，并以外部模型调用为基础开展辅助。

六项Skill按用途分为三组。大纲规划、人物塑造和情节构思主要服务于创作准备与构思，提供结构、人物或剧情方向的建议；上下文续写和文本润色围绕已有正文，分别生成后续候选或调整选中文本的表达；一致性检查结合已有设定与章节内容，提示可能存在的矛盾。这些任务都由作者按需发起，其输出是可供选择的建议或辅助判断。

例如，续写任务需要明确当前写作位置与推进要求，润色任务则需确定选中文本和修改目的。Skill将这些要求交给上下文管理与模型调用环节，并按任务用途呈现结果。作者确认后，候选才进入相应的正文或创作资料保存流程；未被采用的结果不覆盖正式内容。具体任务流程及提示组织将在系统设计章节中展开。

### 2.4.3 Context Management

长篇小说的创作背景分布在作品信息、人物及关系、世界观、大纲和章节正文等资料中，已有章节摘要也可为回顾前文提供参考。不同任务关注的内容不同，直接提交全部资料既难以突出当前要求，也受到输入规模和处理开销的限制。长文本推断研究讨论了长输入涉及的计算与存储开销[P08]；Re³则在长故事生成中动态组合计划与此前故事状态，为下一段生成准备背景[P14]。

本系统借鉴按生成阶段组织相关信息的思路，将Context Management设计为任务上下文管理部分。它根据当前Skill和写作位置确定资料需求，取得相关内容，进行必要的选择、裁剪与组合，并控制输入规模。组织时区分已确认设定、已有正文、大纲计划和章节摘要，避免将计划中的情节直接当作已经发生的事实。摘要按其来源章节及更新情况使用，当前编辑器内容和作者要求则作为本次任务的直接输入。

在上下文续写中，系统拟结合当前正文、邻近的前文章节、人物设定及必要的情节资料，为模型提供承接背景。在一致性检查中，则围绕人物关系、世界规则和已有事件组织参照内容，与待检查文本共同输入。模型给出的冲突提示仍可能存在遗漏或误判，需要作者结合原文复核。上下文管理的作用是准备适合当前任务的信息，其实际效果由后续系统测试检验。

Context Management与MCP分别承担内容组织和资料访问职责。前者决定需要哪些上下文以及如何组合，后者通过规范化协议接口访问系统内已保存的创作资源和必要查询工具。按本项目方案，上下文续写与一致性检查需实际经过MCP协议链路取得相关资料，再与当前请求中的编辑内容、选中文本和作者要求合并。当前输入可直接进入上下文管理，无需先保存再读取。下一节将介绍MCP协议及其在这种访问方式中的作用。

## 2.5 MCP协议

MCP（Model Context Protocol，模型上下文协议）是一种连接AI应用与外部数据、工具的开放协议，通过统一的消息和能力描述方式，支持上下文资料访问与工具调用。本系统采用2025-11-25版规范作为设计依据，将MCP用于智能创作任务与系统已保存资料之间的访问衔接，使不同任务能够按需获取背景信息。[MCP规范概述](https://modelcontextprotocol.io/specification/2025-11-25)

MCP架构包含Host、Client和Server三种角色。Host是组织AI应用及管理客户端的宿主；Client位于Host内部，负责与相应Server建立协议连接并交换消息；Server提供可访问的资料与能力。[架构规范](https://modelcontextprotocol.io/specification/2025-11-25/architecture)双方先通过初始化确认协议版本、交换支持的能力，客户端收到初始化响应后发送就绪通知，再进行资源读取和工具调用。[生命周期规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)

Resource主要表达可读取的上下文资料，由URI标识，客户端通过资源读取请求取得内容。Tool则表达可调用的操作，通过工具名称和输入描述说明如何提交参数并获得结果。[Resources规范](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)及[Tools规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)本系统拟将作品概要、人物及关系、世界观、大纲、章节和已有摘要作为资源，使用get_chapter_window等查询工具按作品、章节位置和范围取得所需前文。这些是本项目的资料与查询设计，具体定义留到系统设计章节。

Streamable HTTP是MCP的传输方式之一，使用HTTP承载JSON-RPC 2.0协议消息。客户端以POST向MCP端点发送消息；对于请求，服务端可返回JSON响应或通过SSE传送消息，客户端也可通过GET请求建立接收服务端消息的SSE流。协议允许服务端不提供该GET流并返回相应状态，因此采用这种传输不要求每次调用都流式返回。[传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)HTTP负责传输，JSON-RPC组织协议方法与结果，其含义与普通业务REST接口不同。

本系统拟由Spring Boot后端的AI编排部分承担Host职责，在同一应用中集成Client与Server，通过回环HTTP完成真实协议通信。Vue仍通过普通业务接口发起创作请求，Server复用创作查询Service提供资料。这种部署是本项目的工程选择：保留单体应用结构，同时让资源访问实际经过MCP消息和传输处理，而非以Java方法直调代替协议链路。

在AI流程中，Writing Skill组织任务，Context Management确定资料范围并调用MCP访问已保存资源和查询工具。上下文续写与一致性检查拟以这一真实链路取得相关背景；当前未保存正文、选中文本和作者要求可直接进入上下文管理，无需先写库再读取。组织后的上下文交给LLM生成候选或检查结果，由作者确认后经普通业务接口保存。MCP承担资料访问职责，生成内容的适用性仍需作者判断与系统测试验证。

## 2.6 系统技术框架

本系统面向PC端小说创作者，拟采用前后端分离的B/S架构，由浏览器提供创作界面，Spring Boot单体后端处理业务与智能辅助任务，MySQL保存相关数据。该结构将页面交互、业务处理和数据管理分开组织，同时在同一后端中衔接常规写作与AI辅助，适合本项目围绕作品持续维护资料和正文的需求。

前端以HTML5、CSS3和JavaScript为基础，拟使用Vue 3与Element Plus组织工作台、作品与章节、正文编辑及创作资料页面。Vue Router管理页面入口，Pinia共享当前作品等必要状态，Axios发送HTTP业务请求，ECharts展示个人创作统计。组件化页面用于协调目录、编辑区和AI辅助面板，使资料维护与候选结果查看围绕当前作品展开。

后端基于Java 17，当前工程采用Spring Boot 3.5.16和MyBatis-Plus 3.5.17。系统拟由Spring MVC提供REST风格业务接口，结合JWT及业务规则校验用户身份、角色和数据归属，再由Service处理请求，通过MyBatis-Plus与MySQL完成持久化。创作统计由后端按当前用户的真实业务记录汇总后返回前端，这种分工对应了创作数据之间的关联和统一管理需要。

智能辅助部分拟由Writing Skill组织大纲规划、人物塑造、情节构思、上下文续写、文本润色和一致性检查六项任务。Context Management按任务选择、裁剪并组合创作背景，LLM据此生成候选内容或分析结果。任务组织与资料准备分别承担职责，以适应构思、修改和检查对输入内容的不同要求。

已保存资料的访问拟通过MCP完成：后端同一应用内集成Client和Server，Client经真实Streamable HTTP回环通信访问Server，Server复用业务Service查询授权范围内的资源。上下文续写与一致性检查需实际使用这一协议链路，Vue仍只访问业务接口。当前未保存正文、选中文本和作者要求可直接加入上下文，无需先写库再读取。最终结果返回前端，由作者决定采用、修改或放弃，确认后经普通业务接口保存。各项技术据此分别服务于交互、业务、资料访问和生成处理，具体模块、实现与验证将在后续章节展开。

## 2.7 本章小结

本章围绕小说智能辅助创作系统的开发需要，介绍了Vue 3及相关前端技术、Spring Boot、Spring MVC和MyBatis-Plus后端技术，以及MySQL数据库，分析了技术选型理由，并说明前后端分离框架中界面交互、业务处理与数据存储的协作关系。这些技术分别用于组织创作界面、处理业务请求和保存相关创作数据。

针对智能辅助创作，本章区分了大语言模型的文本生成与分析、Writing Skill的任务组织、Context Management的上下文准备，以及MCP通过真实协议通信访问创作资料与查询工具的职责，明确候选内容由作者确认后保存的设计原则。下一章将结合小说创作者的实际使用场景，对系统功能需求与非功能需求进行分析。
